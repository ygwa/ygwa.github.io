# 技术博客写作 Skill

用于撰写结构清晰、逻辑严谨、具备工程思维的技术博客文章。  
目标是形成"理论 → 实践 → 优化 → 验证 → 抽象"的认知闭环，避免流水账与知识搬运。

---

## 一、工作流与交互规范（严格执行）

在开始正式输出正文前，必须遵循以下步骤：

1. **信息确认**：如果用户的指令中未明确包含以下 4 项信息，请**根据用户提供的话题自行推断**，并在回复的最开头以 Markdown 引用块（`>`）的形式向用户声明你的设定；如果信息严重不足，请优先反问用户。
   - **文章类型** — 系统讲解 / 原理探究 / 过程分享 / 学习笔记 / 技术思考
   - **深度等级** — L1（快速笔记）/ L2（系统讲解）/ L3（深度分析）
   - **目标读者** — 初级 / 中级 / 架构向
   - **核心问题** — 一句话总结文章解决的核心问题
2. **生成大纲**：根据选定的【文章类型】强制结构，输出文章大纲。
   - *特别提示：如果是 **L3 深度**的文章，必须在此步骤停顿，等待用户确认大纲后，再**分章节逐步生成**正文，以避免输出中断和质量下降。*
3. **输出正文**：严格按照【写作风格】与【深度等级】逐章节填充内容。
4. **元数据与自检**：正文生成完毕后，输出符合规范的 Hugo Front Matter，并进行【质量标准自检】。

## 二、文章类型与结构约束

### 1️⃣ 技术系统讲解类（推荐默认）
**适用场景**：架构设计、中间件分析、性能优化、原理解析、新技术学习。
**强制结构**：
1. 技术定义与核心原理（是什么 + 解决什么 + 核心机制）
2. 应用场景分析（适用场景 + 不适用边界）
3. 工具或实操案例（代码示例 + 最小可运行案例）
4. 实践中的问题（常见误区 + 性能瓶颈 + 隐含成本）
5. 优化方案与设计改进（架构改进 + 参数调优 + 替代方案）
6. 效果验证与评估（验证方式 + 关键指标 + 对比数据）
7. 总结抽象（方法论提炼 + 一句话归纳）
*禁忌：跳过原理直接讲工具 | 没有问题分析就给优化 | 没有验证就声称有效*

### 2️⃣ 原理探究类（偏底层分析）
**适用场景**：源码阅读、底层机制、框架内部原理。
**结构**：问题背景 → 核心概念 → 机制拆解 → 流程分析 → 优缺点 → 总结抽象

### 3️⃣ 过程分享类（实践复盘）
**适用场景**：项目实践、系统搭建、工具使用、踩坑记录。
**结构**：背景目标 → 整体方案 → 关键步骤 → 问题解决 → 最终效果 → 经验总结

### 4️⃣ 学习笔记类（知识整理）
**适用场景**：概念整理、技术对比、读书笔记。
**结构**：核心概念 → 关键知识点 → 对比分析 → 个人理解

### 5️⃣ 技术思考类（观点输出）
**适用场景**：技术趋势分析、架构方法论、新方向思考。
**结构**：现象描述 → 问题分析 → 本质拆解 → 趋势判断 → 个人观点

## 三、写作风格规范

### 语言要求
- 简体中文，句式简洁，一句一观点，避免冗长复合句。
- 避免堆砌形容词、空泛表达和流水账式叙述。

### 表达原则（四大必须）
- **必须解释"为什么"** — 不只说是什么，要说为什么这样做。
- **必须说明"什么时候不适用"** — 明确技术的边界和局限。
- **必须讨论"代价是什么"** — 深入权衡和成本分析。
- **必须给出"如何验证"** — （针对实操类文章）提供可重现的验证方法。
- *提示：每个小节回答一个问题，小节标题应尽量具备问句属性。*

## 四、深度等级控制与生成策略

| 等级 | 预估字数 | 特点 | 应用 | 生成策略 |
|-----|-----|------|------|------|
| **L1** | 1000-1500 | 知识整理，快速笔记 | 学习笔记、概念 | 单次直接生成 |
| **L2** | 1500-3000 | 原理 + 实操，系统讲解 | 技术方案、工具 | 单次直接生成 |
| **L3** | 3000+ | 原理 + 优缺点 + 性能对比 + 抽象 | 架构设计、深度分析 | **必须分章节输出** |

*注：L3 必须包含机制解释 + 优缺点分析 + 性能或设计对比 + 方法论抽象。*

## 五、代码块与表格规范

### 代码块要求
- 必须指定语言类型（bash, java, python, yaml, sql 等），禁止无标记代码段。
- 代码块前后必须有上下文说明，说明代码作用及参数含义。
- 长代码段应分段展示，逐步递进。

### 表格规范（用于对比、选型）
必须使用标准 Markdown 表格语法：
```markdown
| 项目 | 对比维度 | 优势 | 劣势 |
|-----|------|------|------|
| 方案A | ... | ... | ... |

```

## 六、Hugo Front Matter 规范

文件路径预设：`content/writings/<article-slug>/index.md`

**Front Matter 结构生成标准**：

```yaml
---
title: "文章标题"
date: YYYY-MM-DDTHH:MM:SS+08:00
draft: false
description: "一句话总结文章核心内容（必填）"
tags:
- 技术栈标签
- 主题标签
- 内容类型标签
---

```

**自动生成规则**：

* `slug`：**必须将中文标题精准翻译为英文**，转化为全部小写，并用连字符 `-` 连接（例如：`how-to-optimize-redis`）。
* `date`：获取当前时间，严格采用 `YYYY-MM-DDTHH:MM:SS+08:00` 格式。
* `tags`：每篇文章精准提取 3-5 个标签。

### 标签参考库

* **技术栈（小写英文）**：java, spring-boot, docker, kubernetes, redis, mysql, mongodb, go, rust, python, nodejs 等。
* **内容类型（中文）**：原理分析, 项目实践, 架构设计, 性能优化, 源码阅读, 技术思考, 学习笔记, 工具使用。
* **专栏标签**：ai-agent, sdd, knowledge-system, workflow, 系统设计。

## 七、质量标准与自检条件（出稿前最终确认）

每篇文章在完成主体内容后，需核对以下七项标准。
**【豁免规则】**：【学习笔记类】与【技术思考类】可豁免“有实践”与“有验证”；其余类型必须 **全部满足 7 项**，缺少两项以上必须自我重写修正。

* ✅ **有问题** — 清晰表述要解决的问题背景
* ✅ **有原理** — 从第一性原理讲解机制
* ✅ **有实践** — 提供可运行的代码示例或最小案例
* ✅ **有分析** — 分析优缺点、性能、设计权衡
* ✅ **有优化** — 给出改进方案或最佳实践
* ✅ **有验证** — 说明如何验证、测试、量化效果
* ✅ **有抽象** — 提炼方法论，一句话总结

## 八、常见错误防范

| 错误表现 | ❌ 错误示例 | ✅ 纠正方向 |
| --- | --- | --- |
| **流水账** | "我用了 Docker，然后配置了 xxx，最后成功了" | 说明为什么选 Docker，解决什么环境问题，优化了什么流程 |
| **知识搬运** | 原样复述官方文档的 API 列表 | 结合实战案例，只讲核心 API，并说明适用场景和坑点 |
| **无原理** | 直接给出大段配置代码 | 先用图解或文字解释核心工作原理，再给具体配置示例 |
| **无验证** | "这个优化配置可以大幅提升性能" | 给出具体的压测方案、测试数据对比（如 QPS 提升了多少） |
| **孤立代码** | 贴出代码段但不解释上下文 | 说明代码的作用、所属文件、调用关系、关键参数含义 |
