预编译通常能提升 SQL 查询性能：参数化语句可以复用执行计划，减少编译成本。但在真实业务中，性能表现并不总是线性提升。

然而，预编译技术并非总是适用且无懈可击的。在实际应用中，可能会遇到一些问题和挑战。例如，在某个场景下，当系统需要处理超过1亿条记录的数据量时，即使采用了预编译技术，查询速度仍然会变得缓慢甚至导致超时现象的发生。尽管从接口层面进行了充分的优化，并建立了相应的索引以加速查询过程，但在实际运行环境中，由于数据规模的巨大差异，这些措施可能无法完全解决问题。

因此，在面对大规模数据集时，需要更深入理解预编译机制的边界，并结合业务与数据分布做实证分析。

<!--more-->

在最近的项目中，使用预编译 SQL 进行数据查询时经常出现稳定性超时。客户端执行同样查询却能在 500ms 左右返回。这个反差提示：程序端的 SQL 形态可能影响了执行计划。

首先我排查了事务隔离级别、锁竞争与数据热点等因素，未能解释程序端与客户端的差异。于是把焦点转向 ORM 生成 SQL 的方式。

在网上寻找解决方案的过程中，我发现了一些有价值的建议。其中一条是关于 fetch size 配置的调整，另一条则是建议将 MyBatis 的 `#{}` 改为 `${}`。

## MyBatis 参数占位符的区别

这里要先澄清一个常见误区：`#{}` 和 `${}` 是 **MyBatis 占位符语法**，不是 MySQL 数据库本身的参数协议。

- **`#{}`（推荐默认）**：MyBatis 会把它处理为 JDBC 预编译参数（`?`），由驱动进行参数绑定。优点是更安全（防 SQL 注入）、更规范，通常也是大多数场景的首选。

- **`${}`（字符串拼接）**：MyBatis 直接把内容拼接到 SQL 文本中，不走 JDBC 参数绑定。它更接近“动态 SQL 文本替换”，灵活但有注入风险，必须严格白名单控制。

## 解决方案

我在可控场景中尝试将部分 `#{}` 改为 `${}`，并进行了基准验证。结果是查询时间稳定在 500 毫秒左右。这里的关键结论不是“`${}` 一定更快”，而是：**不同参数传递方式会影响执行计划与优化器行为**，必须结合具体 SQL、数据分布和索引设计来评估。

## 问题分析

至此，我对问题的定位逐渐清晰——并非“预编译一定慢”，而是某些场景下参数化查询和文本查询触发了不同的执行计划。

可能的原因包括：
1. 参数化 SQL 可能触发与文本 SQL 不同的执行计划
2. 统计信息和数据分布变化会放大执行计划差异
3. ORM 生成 SQL 的方式（动态拼接、条件展开）可能影响优化器选择

## 总结

通过这次问题排查，我认识到：
- 预编译并非万能，但依旧应作为默认选择
- `#{}` 与 `${}` 的取舍本质上是“安全性、可维护性、性能”三者权衡
- 性能优化必须以可复现实验和执行计划分析为依据，而不是经验判断

## 适用边界

- 任何涉及 `${}` 的改动都必须有严格白名单与审计，否则容易引入 SQL 注入风险。
- 仅凭单次基准结论做全局替换风险很高，应结合执行计划与压测结果逐条验证。
